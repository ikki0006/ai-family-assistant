# ADR-0025: リマインドと独立した共有リスト

## Status

Accepted (2026-10-06)

## Context

行きたい店・公園などを複数リストとして管理し、自然文で表示・追加・修正・削除したい。表現の違いによる重複を避け、意味が曖昧なら確認したい。

## Decision

- リストはD1を正本にし、会話要約・長期記憶・通知から分離する。既存の操作判定にcollectionを追加し、リストと項目のID・名前を渡す。通知日時や予定を生成しない。
- 意味が同じ名前はLLMが既存IDへ対応づける。曖昧な場合はclarifyとクイックリプライで確認する。明白な表記ゆれは純粋関数で正規化し重複作成を防ぐ。改名は旧名を別名として最大5個保持する。
- D1のグループ単位JSONにリストと項目を保存する。20リスト・各50項目・合計200項目に制限する。名前と項目名は操作判定へ渡し、メモ全文は表示時にDBから取得する。
- versionによる比較更新と、本文を含まないイベントIDの記録を同じD1 batchで実行する。削除後の再配信で項目を復活させない。他グループのデータは参照・更新しない。
- リスト丸ごとの削除は本人のボタン確認を必須とし、確認時のversionから変化していれば停止する。項目単体の明示的な削除は即時反映する。
- 会話の削除ではリストを削除しない。リスト削除でも元の会話は消さない。それぞれ独立して削除する。

## Consequences

追加インフラは不要だが0008のmigrationが必要。グループ全体で比較更新するため、別リストへの同時変更でも再確認になる場合がある。意味の同一性はモデル依存のため、確認を挟んで誤操作を訂正できるようにする。

## Enforcement

CRUD、表記ゆれ、グループ分離、競合、再送、確認前削除の拒否、ページング、会話からの操作接続と通知非作成をテストする。pnpm verifyで検証する。
